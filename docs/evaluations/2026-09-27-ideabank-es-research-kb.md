## 一、灵感库候选需求评估

**结论先行:以下条目全部维持"暂不实现"。** 当前后端稳定化(A2 迁移/备份)与正式前端补齐
(`/admin`、F9 v2 对接)优先级更高;在真实试用反馈证明痛点前,不并行铺开新功能。

评估维度:价值(对 10 人课题组的真实增益)、成本(后端+前端+测试+运维)、依赖(是否需要别的模块先就位)、
触发条件(什么信号出现才值得捞回)。"最小验收"描述捞回后第一版可测的边界,不是实现计划。

### 1.1 文献阅读清单 / 精读管理

| 维度 | 评估 |
|---|---|
| 价值 | 高。组内共同维护"方向必读清单",新人入门有确定性路径;可承接 F7 已上传的 PDF 资源 |
| 成本 | 中。需要新的关联模型(清单 ↔ 资源 ↔ 成员状态)、若干接口与页面;若做"精读笔记"还要复用文档模型 |
| 依赖 | F7 资源库、F5 标签、统一内容模型;research-kb 若接入可提供候选文献来源 |
| 触发条件 | 出现"新人重复问该读哪些论文""同一篇论文多人重复精读"等真实反馈,且组内愿意维护清单 |
| 最小验收 | 创建清单 → 加入已入库资源 → 标记"未读/在读/已读" → 按方向筛选;权限沿用资源可见性,不做跨组共享 |
| 结论 | 暂不实现;若 research-kb 接入,优先做"从检索结果一键加入阅读清单",避免两套文献入口 |

### 1.2 轻量打卡 / 日志、周报

| 维度 | 评估 |
|---|---|
| 价值 | 中高。周报是"进度监督"最直接的补充;轻量日志可为周报提供数据地基,减少一次性回忆成本 |
| 成本 | 中。周报需要提交/查看/按周聚合;打卡若做提醒还要引入定时任务与通知 |
| 依赖 | 项目/任务(F9)已可关联;通知(见 1.5)是提醒的前置;导师可见性需权限矩阵先定 |
| 触发条件 | 导师明确要求周报机制,或组会中反复出现"这周做了什么说不清"的情况 |
| 最小验收 | 成员每周一条:完成/阻塞/下周计划,可关联任务;supervisor 只读查看;不做评分与自动考核 |
| 结论 | 暂不实现。周报优于打卡:先解决"结构化表达",再考虑"行为记录";打卡单独做容易变成形式负担 |

### 1.3 组会分享排期

| 维度 | 评估 |
|---|---|
| 价值 | 中。解决"每周谁讲"的协调问题,可见性高、演示效果好 |
| 成本 | 中低。本质是日历型轻量实体(时间/主讲/主题/状态),无复杂算法 |
| 依赖 | 成员列表、通知(可选);与"日历系统"防跑偏清单边界需先讲清:只做组会排期,不做通用日历 |
| 触发条件 | 组会排期仍靠聊天记录人工维护,且出现遗漏/撞车 |
| 最小验收 | 创建排期(时间/主讲/主题)→ 列表按时间排序 → 主讲本人或 admin/supervisor 可改;到期提醒可后置 |
| 结论 | 暂不实现。成本最低,适合作为"后端稳定化完成后第一个小功能"的候选,但需先明确不扩展成通用日历 |

### 1.4 导师只读总览 + 学生档案卡

| 维度 | 评估 |
|---|---|
| 价值 | 高。直击"导师快速掌握进展"的核心诉求,是阶段 B 明确规划方向 |
| 成本 | 中高。总览需要跨项目/任务聚合与逾期口径;档案卡要聚合成员的任务、文档、资源,权限与隐私边界复杂 |
| 依赖 | supervisor 角色语义已在 Casbin 预留;任务逾期统计已有 `stats.overdue` 基础;需先定"导师能看到哪些私有内容"的产品决策 |
| 触发条件 | 导师实际使用平台并反馈"看不过来";且隐私边界(尤其私有笔记是否对导师可见)已明确 |
| 最小验收 | supervisor 只读查看项目进度/逾期任务/成员任务分布;**默认不读学生私有笔记**,除非学生显式公开 |
| 结论 | 暂不实现,但列为阶段 B 首选。关键风险是隐私边界,未定清前不写代码 |

### 1.5 通知推送(站内/微信机器人)

| 维度 | 评估 |
|---|---|
| 价值 | 中高。任务指派、临近截止、评论回复是即时性需求;能显著提升回访率 |
| 成本 | 高。需要事件定义、幂等、重试、已读状态与隐私边界;微信机器人还要处理出网与合规 |
| 依赖 | 后端事件与后台任务机制;roadmap 阶段 D 已将其排后 |
| 触发条件 | 已有稳定日活,且用户反馈"错过任务/评论";先做站内通知,再评估微信 |
| 最小验收 | 站内通知列表 + 未读数;覆盖任务指派与评论回复两类事件,幂等且失败可重试;不外发敏感内容 |
| 结论 | 暂不实现。通知必须建立在稳定事件模型上,直接接入核心事务风险高 |

### 1.6 其他已在库条目(简述)

- **文档 ↔ 资源关联 / 文档 ↔ 任务互转**:价值中高,但依赖统一引用模型;建议与"编辑器内嵌引用块"同批设计,避免三次改数据模型。暂不实现。
- **编辑器内嵌引用块**:价值中,前端富文本成本高(当前是 Markdown);触发条件是正式前端上手写体验成为主要瓶颈。暂不实现。
- **资源知识图谱 / 复杂社交 / 积分激励**:价值低或与"10 人私人平台"定位不匹配,维持防跑偏清单,暂不实现。
- **论文元数据(F8)重设计**:依赖真实文献管理痛点与 research-kb 定位划分,单独评估,不在本报告结论内。

### 1.7 灵感库优先级建议(仅排序,不是排期)

```text
阶段 B  导师只读总览(隐私边界先定) + 逾期任务增强
阶段 B  周报(若导师确认需要)
阶段 C  文献阅读清单(与 research-kb 接入一并设计)
阶段 C  文档↔资源关联 + 任务互转(统一引用模型一次做)
阶段 D  站内通知 → (可选)微信机器人
随时    组会排期(成本最低的小功能,避免扩展成通用日历)
```

## 二、引入 Elasticsearch 的评估

### 2.1 结论

**当前不建议引入 ES。** 10 人以内、内容量在千级到万级时,Postgres 现有
`ILIKE`/`ts_rank` 完全够用;引入 ES 带来的运维、数据同步一致性和权限过滤风险,
远大于它此刻能提供的检索增益。建议按
`Postgres FTS/pg_trgm → pgvector(语义检索) → 才评估 ES` 的顺序演进。

### 2.2 若引入 ES,可以获得的提升

| 能力 | 说明 | 对 LabNexus 的价值 |
|---|---|---|
| 中文分词 | IK/结巴等中文分析器,替代 `LIKE` 的子串匹配 | 高。当前中文搜索依赖 `ILIKE`,"隐写/信息隐藏"等近义表达召回弱 |
| 相关度排序 | BM25 + 字段加权(标题 > 正文)+ function_score | 高。当前按标题优先 + 时间,排序表达力有限 |
| 高亮 | 命中片段 `highlight` 返回给前端 | 中高。搜索结果可直接展示命中上下文 |
| 多字段聚合 | 按标签/类型/作者/项目做 facet 聚合 | 中。替代多次 `GROUP BY` 查询 |
| 同义词 / 模糊 / 拼音 | synonym、fuzzy、pinyin 插件 | 中高。提升中文输入的容错 |
| 跨类型统一搜索 | 文档、资源、任务、论文统一索引 | 中。F6 已做聚合,但语义仍以 `LIKE` 为主 |
| 大语料性能 | 倒排索引在海量数据下更稳定 | 低(当前)。千级数据无性能压力 |

### 2.3 为什么不建议现在引入

- **规模不匹配**:课题组内容量在千级,Postgres 顺序扫描/索引响应在毫秒级;ES 的横向扩展能力用不上。
- **运维成本**:多一个有状态服务要部署、监控、备份、升级;当前是"0 成本演示 + 单人维护"阶段。
- **一致性风险**:ES 是外部索引,写入需要双写或 CDC,容易出现"库里有、搜不到"或"删了还能搜到";
  现有 `app.Build` 单进程、单数据库模型会显著复杂化。
- **权限过滤风险**:搜索结果必须按 `visibility`、项目成员、上传者过滤,否则私有内容经搜索泄露;
  该逻辑需要在索引层再实现一遍,与"权限只走统一 `Can`"原则容易漂移。
- **数据出界**:若用云 ES,内部笔记/未发表成果会离开私有部署边界,与课题组数据治理冲突。
- **有更轻的替代路径**:Postgres 原生 FTS(`tsvector`/`zhparser`)、`pg_trgm` 模糊匹配、`pgvector`
  语义检索,都能在同一数据库内完成,无需额外服务与同步链路。

### 2.4 触发阈值(建议,满足任一才重新评估)

1. 搜索对象总量稳定超过 **10 万级**(文档+资源+任务+论文条目);
2. 搜索接口 p95 持续超过 **300–500ms**,且已排除慢查询/SQL 优化空间;
3. 产品明确需要 **中文分词、高亮、同义词、facet 聚合**等 Postgres 难以低成本满足的能力;
4. research-kb 接入后,需要**跨服务统一知识检索**(外部论文语料 + 组内内容);
5. 出现真实用户投诉"搜不到",且分析证明是召回质量(而非数据缺失/权限)导致。

### 2.5 分阶段检索演进建议

```text
第 1 步(现在)  Postgres 现状:ILIKE + 标题优先排序;补充分页与类型筛选,不引入新服务
第 2 步          中文全文检索:tsvector + zhparser/pg_trgm,同库内实现,零新增运维
第 3 步          语义检索:pgvector 向量列 + 混合排序(RRF),复用 research-kb 经验
第 4 步(最后)    仅在触发阈值满足时评估 ES/OpenSearch;若引入必须先解决
                 索引-数据库同步、权限过滤、删除一致性、私有部署与备份
```

## 三、research-kb 项目了解与接入评估

> 本节基于只读查阅 `/Users/alan/research-kb`(分支 `mvp`,工作区干净,本次未做任何修改),
> 来源:`CLAUDE.md`、`docs/models/00系统模块规划.md`、`docs/models/06评测基准设计.md`、
> `docs/eval/2026-09-13-eval-report.md`、`docs/superpowers/specs/2026-09-12-info-sec-literature-kb-design.md`、`README.md`。

### 3.1 项目定位

research-kb 是一个**面向信息安全课题组的外部文献知识库 + RAG 问答系统**:
用中文自然语言提问,系统在**组内持久化的文献库**里做查询改写 → 混合检索 → 重排,
给出**带引用、按研究思路组织**的中文答案,并提供本地 Web 界面。

它与 LabNexus 的分工天然互补:

| 维度 | LabNexus | research-kb |
|---|---|---|
| 定位 | 组内社区平台(人 + 协作 + 组内内容) | 外部文献知识库(论文 + 检索问答) |
| 核心资产 | 成员、帖子、笔记、资源、项目任务 | 论文元数据/摘要、向量、检索与问答链路 |
| 覆盖 | 组内产生的私有内容 | 白名单期刊的外部公开文献 |
| 明确排除 | 不是文献管理/RAG 系统 | 不做组内未发表成果/笔记/代码管理、不替代 Zotero |

两者在"**论文/文献**"上存在交集:LabNexus 的 F7 用 PDF 文件管理论文,research-kb 用元数据+摘要做检索问答。
接入时应明确"**检索问答走 research-kb,组内讨论/任务/笔记走 LabNexus**",避免两套文献入口重复。

### 3.2 技术栈与现状(截至 2026-09)

- **技术栈**:Go 单二进制 + PostgreSQL 16 + pgvector;云端 LLM/嵌入/重排 API;templ + htmx 服务端渲染;
  查询改写 + 向量/pgvector + Postgres `ts_rank` + RRF 融合 + DashScope `qwen3-rerank`;CLI/Web/JSON API 三种入口。
- **语料**:12 本信息安全/网络期刊,2022–2026,约 **19,937 篇**论文;chunks 约 **1.46 万**,`section` **全部为 abstract**;
  摘要覆盖约 **73%**,无摘要论文没有向量;嵌入 **2048 维**,超过 pgvector ANN 2000 维上限,**只能顺序扫描精确检索**。
- **已知覆盖缺口**:IoT-J 因 OpenAlex 4000 翻页上限缺约 **9855 篇(该刊约 71%)**,其余期刊每刊缺 1–6 篇;会议未接入
  (OpenAlex 对近年 CS 顶会 source 归属缺失,需换 Semantic Scholar/DBLP)。
- **评测**:`eval/golden.yaml` 3 方向/10 题/73 篇期望论文;门禁设计 G1 语料完整性、G2 引用合法率、G3 诚实率;
  实测 `Recall_corpus@20 = 0.671`,无重排 0.342,无查询改写 0.055,`Precision@20 ≈ 0.245`,`Contamination@20 ≈ 0.01`;
  查询改写带来的增益最大(约 12×),重排次之。
- **已落地**:采集入库、摘要向量化、混合检索、重排、带引用综合、Web/CLI/JSON、可复现评测。
- **未落地/风险**:无 PDF 全文与解析层(最大盲区,压住端到端上限);G1/G2/G3 尚未自动门禁;无鉴权(仅本机/内网);
  无调度与告警;无成本核算;语料无快照版本化;服务本体无容器编排/反向代理。

### 3.3 接入 LabNexus 的建议(分阶段,先不合并代码)

**阶段 0(现在)——保持独立,明确边界**

- 不合并两个代码库。LabNexus 用 Go+Gin+GORM,research-kb 用 pgx+templ+htmx,合并成本高且会拖慢各自演进。
- research-kb 继续把精力放在自己的硬缺口:语料完整性、PDF 全文解析、鉴权、评测门禁与部署稳定性。
- LabNexus 保持"组内协作"定位,不新增文献 RAG 功能。

**阶段 1——服务间集成(推荐的第一步)**

- research-kb 暴露稳定的 **JSON API**(已有 `POST /ask`、`GET /paper/{id}`、`GET /healthz`)。
- LabNexus 增加 `/api/kb/*` 代理/网关路由,由 LabNexus 负责**身份认证与授权**,research-kb 负责检索问答。
- 服务间用**服务 token 或内部 JWT** 校验,research-kb 不直接暴露公网;两边数据库暂不共享。
- 权限语义:登录成员即可用检索;敏感能力(如未来接入组内未发表成果)必须回到 LabNexus 的 `Can` 决策。
- 该阶段**不改 LabNexus 现有契约的既有端点**,只在契约中新增 `/api/kb/*`(需先评审)。

**阶段 2——知识资产互通**

- 评估是否共享 **paper/corpus ID**:LabNexus 的 F7 资源可标注 research-kb 的 paper id,实现"从问答引用一键跳资源"。
- 评估**双向引用**:LabNexus 笔记/任务引用 research-kb 论文;research-kb 答案引用组内笔记(需权限过滤)。
- 这些都需要先定"权威 ID 与数据所有权",不要急着做双写。

**阶段 3(远期)——统一检索**

- 只有出现跨"组内内容 + 外部论文"的统一检索需求时,再评估统一索引或联邦检索。
- 届时回到本报告第二节的 ES 触发阈值判断;过早统一会把两个系统的复杂度耦合在一起。

### 3.4 接入风险清单

| 风险 | 说明 | 建议对策 |
|---|---|---|
| 数据出界 | research-kb 用云端 LLM/嵌入/重排,组内敏感知识若进入会离开私有边界 | 外发内容限定为公开文献;组内私有内容不进入 research-kb,或先换本地模型 |
| 无鉴权 | research-kb 目前无 auth,直接暴露会造成滥用与数据风险 | 接入前先加服务间 token;公网入口只经 LabNexus 网关 |
| 覆盖不穷尽 | IoT-J 缺 71%、会议未接入,直接影响"找全"承诺 | 接入前先修语料完整性并落 G1 门禁,否则问答可信度无法验证 |
| 无全文 | 只有摘要级检索,事实/对比型问题回答不了 | 先做 PDF 解析垂直切片;接入问答时明确标注"摘要级"能力边界 |
| 运维薄弱 | 无调度/告警/成本核算/快照 | 接入前补齐最小运维:定时增量、失败告警、语料版本 |
| 双系统漂移 | 两套文献入口、两套数据集 | 明确"LabNexus 管组内,research-kb 管外部文献";只在引用层交汇 |

### 3.5 一句话建议

**现在做"边界与接口"的设计对齐,不做代码合并。** 最划算的第一步是:
research-kb 先补鉴权与语料门禁,LabNexus 预留 `/api/kb/*` 网关位置,未来用服务 token 打通;
等两边各自稳定后,再从"论文引用互通"逐步走向统一检索。
