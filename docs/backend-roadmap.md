# LabNexus 已有功能总结与后端开发规划

> 阶段 2 基础功能已完成；后续开发继续遵循 SDD + TDD、MVC 轻量分层和契约先行。

## 一、已有功能

### 1. 账号、角色与权限

- 邀请码注册，默认角色为 `student`。
- 用户名密码登录，JWT access token + Redis refresh token。
- refresh token 轮换、注销撤销。
- 个人资料和密码修改。
- 管理员查看用户、修改角色、管理邀请码。
- 角色：`admin`、`supervisor`、`student`。
- 私有内容按作者和项目成员隔离；越权访问不泄露私有对象信息。

### 2. 个人空间

- 每个用户有独立个人空间。
- 支持目录树的创建、重命名、排序和删除空目录。
- 文档可归档到目录，也可以不放入目录。

### 3. 文档、笔记与帖子

- `Document` 是统一内容实体。
- `visibility=private` 表示个人笔记，`visibility=public` 表示公开帖子。
- 支持创建、编辑、软删除、置顶和可见性切换。
- 公开文档进入社区信息流。
- 支持标签、点赞、评论和回复评论。
- 撤回公开状态时保留评论和点赞数据。

### 4. 社区信息流

- 支持最新和基础热门排序。
- 点赞为 toggle 行为。
- 支持评论、回复和作者删除评论。
- 支持统一分页参数及分页响应。

### 5. 标签与搜索

- 支持创建标签、给文档和资源打多个标签。
- 支持按标签查看文档和资源。
- `/search` 聚合搜索文档、资源和任务。
- 当前使用数据库 `LIKE`，适合 10 人以内课题组的 MVP。

### 6. 资源库

- 支持链接和本地文件两类资源（论文以 PDF 文件形式上传）。
- 支持上传、下载、浏览器内预览（PDF/图片/文本/视频）、编辑、删除、标签、描述、类型筛选、关键词检索和分页。
- 文件上传带扩展名白名单 + 内容 MIME 双校验，普通文件 50MB、视频 100MB 上限。
- 文献元数据（DOI/arXiv 自动抓取）已废弃，重做后再引入（见 specs/f8-paper-meta.md）。

### 7. 项目与任务

- 支持项目创建、项目成员、里程碑和任务管理。
- 任务支持负责人、优先级、截止日期、里程碑，以及文档/资源关联。
- 任务状态机在 service 层校验：`todo → in_progress`、`in_progress → blocked`、`blocked → todo/in_progress`、`in_progress → done`，`done` 为终态。
- 支持按状态、负责人和里程碑筛选任务。

### 8. 工程质量

- 技术栈：Go 1.25、Gin、GORM、PostgreSQL、Redis。
- 架构：模块化单体，`handler → service → repository`。
- 生产与集成测试共用 `app.Build` 装配入口。
- 已有 service 单元测试、handler 测试、真实数据库集成测试。
- 已覆盖认证安全矩阵、权限隔离、边界输入、资源上传、搜索聚合和任务状态机。
- `make check` 是提交前质量门禁；已有前端诊断、端到端和 smoke 检查。

## 二、当前后端设计基线

```text
HTTP Request
  → Gin Router
  → Auth Middleware
  → Handler（参数、状态码、响应）
  → Service（业务规则、权限、事务）
  → Repository/GORM
  → PostgreSQL / Redis / 文件存储
```

跨模块调用只发生在 service 层。权限继续统一走 `can(user, action, target)`；新增权限必须同时补充规格、契约和测试。开发期使用 GORM AutoMigrate，`docs/schema.sql` 是结构权威文档。上传文件位于 `data/uploads/`，不进入 Git。

## 三、后续后端规划

### 阶段 A：稳定化与可部署性

目标：让现有功能稳定支持课题组试用。

1. 同步规格、API 契约、schema 和 AI 入口文档的实现状态。
2. 从 AutoMigrate 过渡到版本化数据库迁移，建立基线和回滚策略。
3. 增加生产配置校验、JWT secret 校验、上传目录检查和数据库启动检查。
4. 统一错误码、请求日志和关键写操作日志，不暴露数据库内部错误。
5. 限制上传文件大小与类型，随机化文件名，防止目录穿越，处理孤儿文件。
6. 补充 PostgreSQL 数据和上传文件的备份恢复流程。
7. 增加 API 契约测试，校验实际状态码、字段、分页和错误格式。

阶段验收：新环境按 README 可启动，重启不丢数据，错误可定位，上传和权限边界有自动化测试。

### 阶段 B：课题组试用增强

目标：解决真实协作中的进度和责任问题。

1. **supervisor 只读总览**：查看课题组项目、成员任务和逾期任务，不改变学生编辑权限。
2. **逾期任务查询**：增加已逾期、即将到期筛选，先做数据库查询，不急于引入定时任务。
3. **周报记录**：成员提交完成事项、阻塞问题和下周计划；supervisor 可查看。
4. **审计记录**：记录角色、邀请码、成员变更、任务状态变化和文档公开/撤回，第一版只读。

阶段验收：导师能看到项目进展，成员能说明任务阻塞，关键操作可追溯。

### 阶段 C：检索与内容关联

当实际数据量证明基础能力不足时再做：

1. 文档与资源双向关联。
2. 从文档或资源直接创建任务并保留来源关系。
3. 优先评估 PostgreSQL FTS，明确不足后再考虑 Meilisearch。
4. 增加按类型、标签、作者、项目和时间筛选。
5. 论文元数据重设计（paper 类型 + 引用格式，见 specs/f8-paper-meta.md 重做触发条件）。

### 阶段 D：通知与自动化

确认课题组确实需要提醒后再做：

1. 站内通知：任务指派、临近截止、评论回复、成员变化。
2. 通知列表和已读状态。
3. 可选邮件或微信机器人推送。
4. 后台任务、幂等键和失败重试。

通知实现前必须先定义事件、幂等、重试和隐私边界，不直接把微信机器人接入核心事务。

## 四、暂缓内容

暂不做知识图谱、积分激励、复杂社交关系、实时协作、私聊 IM、原生 App、公网开放、访客角色、复杂审批流、日历系统，以及一开始就引入搜索服务、消息队列或微服务。

当前用户规模小，优先保证数据可靠、权限正确和任务流程可用。

## 五、推荐执行顺序

```text
A1 文档状态同步
  → A2 数据库迁移与备份
  → A3 配置/错误/日志/文件安全
  → A4 契约测试和部署验收
  → B1 supervisor 总览
  → B2 逾期任务查询
  → B3 周报
  → B4 审计记录
  → C1 内容关联
  → C2 搜索升级
  → D1 站内通知
```

每一项都遵循：

```text
写 Spec → 更新 API 契约/schema → 先写 RED 测试
→ 最小实现 → 重构 → make check → 人工验收 → 提交
```
